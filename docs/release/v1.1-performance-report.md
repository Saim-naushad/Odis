cloud, production, or enterprise-hardware results, and nothing here is
extrapolated beyond what was directly measured.**

## Methodology

Each run gets a fresh, uniquely-named Docker Compose project + volumes
(`odis-benchmark-<run-id>`), isolating it from every other run — no
accumulated observations, investigations, Kafka offsets, or Prometheus
counters carry across runs. The simulator runs as a host subprocess against
the stack's host-exposed ports; a passive Kafka observer (its own consumer
group, reading from `earliest` on a brand-new broker), an SSE client, and an
API poller (2s interval) all start before the simulator, so every hop's
endpoints are captured live.

**Percentile method**: exact nearest-rank order statistic over directly
observed per-event samples (`rank = round((pct/100) × (n-1))`), not
Prometheus's bucket-interpolated `histogram_quantile`. Any latency sample
that computes negative (clock precision, ordering, a polling race) is
recorded as an excluded/invalid sample and dropped from percentiles, never
silently clamped to zero — every result below reports `excluded_count`,
which was 0 in every reported figure except where noted.

**Repetitions**: due to session time constraints, this evidence pass ran
**one repetition per configuration** rather than the target 3x/2x schedule.
This is a real deviation from the plan, disclosed here rather than
presented as statistically repeated — see Limitations.

**Onset definition**: `CoolingDegradationScenario.tick()` runs the baseline
physics tick *before* updating the cooling-efficiency target for the next
tick, so sample index 1 of any run is provably identical to a healthy
fleet's — the ramp is only observable from sample index 2 onward. This is
pinned by a dedicated unit test
(`tests/backend/simulator/test_scenarios.py::
test_cooling_degradation_onset_lands_on_second_sample`) and used
consistently as `fault_onset_sample_index = 2` throughout.

## Scenarios

- **Scenario A — healthy throughput**: `normal_operation`, no fault,
  measuring baseline throughput/latency/resource growth.
- **Scenario B — fault lifecycle (canonical)**: `cooling_degradation`
  targeting `fuel-cell-stack-01`, with N−4 additional bench-named assets
  providing background load (the 4 real Plant Alpha stacks are always
  present first).
- **Scenario C** — not implemented in this pass, per the explicit scope
  decision to spend available time on repetition/validation depth for A/B
  instead of scenario breadth.
- **Reliability mode** (`--mode reliability`) — run separately, on its own
  ephemeral stack, never mixed with a performance run.

## Scaling and bottleneck observations

- **The fault-inference worker's single-threaded consume loop is the
  primary throughput bottleneck.** Scenario A's `complete_samples_per_second`
  plateaus at 10.61 (50 assets) and 10.77 (100 assets) — essentially flat —
  while raw telemetry volume keeps climbing (85 → 86 events/s). The
  bottleneck is fully saturated by 50 assets; doubling to 100 assets buys
  almost no additional sample-processing throughput.
- **Hop1 (telemetry→inference publish) latency grows roughly linearly with
  asset count** at fixed worker throughput: median 23ms (1 asset) → 523ms
  (10) → 2,547ms (50) → 5,148ms (100), p95 reaching ~10s at 100 assets. This
  is queueing delay building up in front of the saturated single-threaded
  worker, not a per-message processing regression.
- **`valid_inference_results_per_second` actually *drops* from 50→100
  assets** (6.03 → 3.43) even though total sample throughput stayed flat:
  with fixed total worker throughput spread across more assets, a larger
  share of the fixed-duration run is spent inside each asset's own 12-sample
  warm-up window. This is a real, worth-documenting warm-up/scale
  interaction, not a bug — see Limitations for the throughput-denominator
  caveat this implies.
- **Fault-onset-to-recommendation wall-clock time grows sharply with
  background load**: 37s (1 asset) → 41s (10) → 179s (50), and did not
  resolve within the 100-asset run's 380s+15s-drain observation window at
  all — even though the underlying alert transitions and evidence rows for
  other assets *were* still produced correctly in that run (5 alerts, 5
  evidence rows, 0 excluded/invalid latency samples, consumer lag still
  returned to 0). This reads as a benchmark window-sizing limitation
  compounded by the same worker saturation described above, not a pipeline
  failure — the target asset's own alert simply didn't clear the growing
  processing backlog before the window closed.
- **The reasoning-bridge worker never bottlenecks.** Its own processing
  latency (hop3) stays under ~210ms even at 50-100 assets, and its CPU stays
  under 2% average / under 10% peak at every scale tested — corroboration
  and investigation-lifecycle logic is cheap relative to the ML inference
  path.
- **The legacy observation-driven `worker` (deterministic `ReasoningSession`
  pipeline, runs on every ingested observation regardless of faults) is the
  single most CPU-intensive component measured**, not the ML inference
  worker: 43-82% average CPU across scenarios/scales, peaking above 100%
  (Docker's per-core-relative CPU%, confirming it used more than one core's
  worth briefly) at 100 assets in Scenario B. `fault-inference-worker`
  itself stayed under 12% average CPU at every scale tested.
- **A small amount of outbox backlog appeared at the highest concurrency
  tested** (3 pending rows at 100-asset Scenario A's end snapshot, 4 at
  50-asset Scenario B's) — non-zero but small and non-runaway; not observed
  at lower asset counts.
- **No saturation was observed in Scenario A's raw event throughput itself**
  (telemetry events/s) — it kept climbing modestly from 50→100 assets
  (84.87 → 86.18) even as sample-processing throughput plateaued, meaning
  the simulator/API/Kafka ingestion path itself was not the bottleneck at
  any tested scale; the single-threaded fault-inference consumer was.
- **A `normal_operation` (nominally healthy) run at 50 assets produced 4
  alert transitions** — natural model-score variation crossing the alert
  threshold under fleet-wide load, with no engineered fault present. Worth
  flagging as an observed false-positive-rate data point at this specific
  scale/scenario, not a benchmark defect (same live model/policy pipeline
  as every other run).

## Limitations

- **Single repetition per configuration**, not the target 3x (1/10 assets)
  / 2x (50/100 assets) schedule — a real, disclosed deviation from the plan
  due to session time constraints. Every number above is a single
  measurement, not a median across runs; no variance/range data is
  available. This is the most important caveat on every figure in this
  report.
- **100-asset Scenario B's fault-onset-to-recommendation metric did not
  resolve** within the observation window — reported as `null`/"not
  resolved," not estimated or backfilled.
- **`complete_samples_per_second` and `all_inference_results_per_second`
  are currently numerically identical by construction** (every assembled
  sample yields exactly one `fault_inference.v1` event regardless of
  status) — kept as distinct named metrics per the measurement design, but
  they will only diverge if that 1:1 relationship changes in the future
  (e.g. batched publishing).
- **Throughput figures are "including warm-up," not steady-state.** A
  steady-state boundary (`max` over assets of each asset's own 12th-sample
  timestamp) is computed and recorded per run, but a separate steady-state-
  only throughput recomputation was not run in this pass — a candidate for
  a follow-up evidence pass, not fabricated here.
- **A genuine correctness bug was found and fixed mid-benchmark**: the
  original `reasoning_persist_to_api_observed_ms`/`_sse_observed_ms`
  computation matched every `ai_fault_evidence` row against an asset's
  *first-ever* API/SSE visibility rather than the visibility observed after
  that specific row — for assets with multiple evidence rows in one run
  (e.g. `class_changed` updates), this produced negative latencies, which
  the benchmark's own negative-latency safety net correctly caught and
  excluded (7 of 9 hop4 samples excluded in the original 50-asset Scenario B
  run) rather than reporting wrong numbers. The matching logic was fixed
  (`ApiPoller.first_visible_after`/`SseObserver.first_event_for_asset_after`)
  and the affected run was re-executed; the corrected figures are what's
  reported in the table above. Flagged here for transparency, not hidden.
- **Not attempted**: Kafka publish-failure visibility under load (tested
  only in isolation via `--mode reliability`, not concurrently with a
  measured performance run, by design); a true steady-state-only throughput
  pass; Scenario C (noisy/insufficient-data stress).
- **No saturation ceiling was found for raw asset count itself** — 100
  assets ran to completion in every case (all 8 scale-matrix runs exited
  0, no crashes, no data loss, consumer lag always returned to 0). The
  bottleneck found is in the fault-inference worker's single-threaded
  *sample-processing* throughput (~10.7 samples/sec ceiling), not in the
  simulator, API, Kafka, or Postgres layers at the scales tested. No
  extrapolation is made about the true maximum supported asset count beyond
  100.

## Resume-safe numerical claims

Measured, derived, and qualitative claims are kept distinct below.

**Measured (directly observed, single-repetition):**

- Processed 12,927 telemetry events across 100 simulated fuel-cell assets
  at 86.2 events/sec, with a fault-inference worker sample-processing
  ceiling of ~10.7 samples/sec, in a local Docker Compose benchmark.
- Detected and confirmed a simulated cooling-degradation fault and produced
  an operator-facing recommendation in 37.2 seconds wall-clock (1 asset,
  local Docker Compose benchmark).
- Maintained zero duplicate AI-fault-evidence rows when replaying an
  already-processed alert-transition event, and zero Kafka consumer lag at
  the end of every one of 9 benchmark runs (8 performance + 1 reliability),
  in a local Docker Compose benchmark.
- Correctly retained an undispatched outbox row through a live Kafka outage
  and delivered it exactly once after recovery, in a local Docker Compose
  benchmark.

**Derived (computed from measured data, not directly observed as a single
event):**

- Reasoning-bridge processing (confirmed alert → durable investigation
  record) stayed under 210ms at the 95th percentile across every asset
  count tested (1-100), while the fault-inference worker's telemetry-to-
  inference-result latency grew from a 23ms median at 1 asset to a 5.1s
  median at 100 assets — indicating the ML inference path, not the
  deterministic corroboration path, is the throughput-limiting component
  at scale.

**Qualitative (observed pattern, not a single number):**

- Reasoning-bridge worker resource usage stayed low and flat across every
  scale tested (under 2% average CPU), while the legacy observation-driven
  reasoning worker was consistently the most CPU-intensive component
  measured — suggesting the newer Kafka-based AI-fault path is
  significantly cheaper per-observation than the original deterministic
  pipeline it runs alongside.

**Explicitly not claimed**: production scale, real-plant performance,
enterprise throughput, high availability, or an exact maximum supported
asset count beyond the 100 tested.
