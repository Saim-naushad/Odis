# ODIS v1.1 Release Scorecard — Hardening Pass

This document is the output of a full release audit of the v1.1 AI-fault-alert path
(PR161–179): simulator → Kafka → fault-inference worker → reasoning bridge →
Postgres/outbox → Redis/SSE → API → dashboard. It records what was found, what was
fixed, what was deliberately left for a follow-up, and an honest verdict — not a
polished summary written after the fact.

Audit method: six focused, read-only passes across infra/demo, backend
streaming/event-contracts, observability, frontend, tests/CI, and docs/security,
followed by fixes for everything scored Blocker or High, verified live against a
real `docker compose --profile demo up --build` stack (not just unit tests).

## 1. Findings and fixes

| Sev | Area | Finding | Fix |
|---|---|---|---|
| Blocker | Demo | `docker-compose.yml`'s `demo-plant` used `SIMULATOR_TRANSPORT=mqtt`, which never fed the fault-inference worker's Kafka topic — the flagship v1.1 capability was unreachable from the standard one-command demo | Switched to the purpose-built `kafka+http` transport (one tick fans out to both Kafka and HTTP); re-tuned `SIMULATOR_KAFKA_PUBLISH_INTERVAL_SECONDS` to preserve the documented ~6:40 `demo_presentation` pacing |
| Blocker | Outbox | `OutboxDispatcher` marked a row dispatched even when the Kafka-leg publish failed (the publisher swallows exceptions by design) — a Kafka blip silently and permanently dropped that event | `IntegrationEventPublisher.publish()` now returns success/failure instead of `None`; the dispatcher only marks a row dispatched once the Kafka leg actually succeeds (or there is none), and retries it on the next cycle otherwise |
| Blocker | Observability | No Prometheus alert rules existed anywhere; Grafana had zero panels for either new worker despite both being fully instrumented | Added `infra/docker/prometheus/rules.yml` (8 demo/reference alerts) and an "AI Fault Alert Pipeline" Grafana row (7 panels) |
| Blocker | Docs | `RELEASE_NOTES.md`/`CHANGELOG.md` stopped at v1.0.0 — none of the AI-fault-alert work was recorded as a release | Added `[1.1.0]` sections to both |
| High | Frontend | `ActiveFaultInvestigationCard`/`FaultInvestigationHistoryPanel` hid last-good data on a transient background-refetch error, contradicting the documented "durable state stays visible" guarantee | Error banner and content now render independently; added regression tests for both components |
| High | CI | `backend.yml` ran bare `pytest`, silently never running the Postgres concurrency test, contradicting `CONTRIBUTING.md`'s documented `pytest -m "not integration"` | Aligned CI to the documented command |
| High | Docs | `docs/platform/platform-architecture.md` and `docs/platform/docker-runtime.md` predated the two new workers entirely | Added an AI-fault data-flow diagram + trust-boundary table to the former; added both workers to the topology table, architecture diagram, and health/startup-order table in the latter |
| High | Docs | `docs/README.md` didn't link 11 existing, high-quality ML methodology docs — they were effectively invisible to a reviewer | Added an "AI Fault Diagnosis" index section plus a new [AI Methodology](../ai-methodology.md) synthesis page |
| High | Security | `docker-compose.yml`, labeled "production runtime," hardcoded `POSTGRES_PASSWORD`/`DATABASE_URL` — the only setting in that block that wasn't overridable via `.env` | Parameterized with `${POSTGRES_USER:-odis}` etc., same pattern as every other setting; added a "demo default, not production" comment; documented the new vars in `.env.example` |

**Deliberately deferred** (Medium/Low severity — not fixed in this pass, per the
task's own "fix only high-value issues" instruction and this repo's small-PR
philosophy): non-root Dockerfile users; true readiness probes (vs. `pgrep` liveness)
for the two new workers; k8s scrape config for workers that don't have k8s
Deployments yet; outbox row cleanup/archival policy; a dedicated
`FaultInvestigationHistoryPanel`/`useFaultInvestigation` hook test beyond what this
pass added; a CI job that boots the full Compose stack; a from-scratch `pytest -m
integration` full-chain test (the live validation below substitutes for this —
see [Remaining limitations](#remaining-limitations)).

## 2. Live end-to-end validation

Ran `docker compose --profile demo up --build -d` against the fixed configuration
and observed the real system, not a mock:

- All 13 services reported healthy.
- `fault-inference-worker` logs: exactly 11 `warming_up` results per asset, then
  `valid_prediction` at the 12th sample — confirms `LONGEST_WINDOW_SAMPLES=12`
  end to end on live infrastructure, not just in a unit test.
- Within ~2 minutes wall-clock, `GET /monitoring/assets/fuel-cell-stack-01/fault-investigation`
  returned a real, live `cooling_degradation` investigation: `alert_transition_type:
  confirmed`, `corroboration_result: partially_corroborated`, a produced
  recommendation, full provenance (`model_hash`, `policy_hash`,
  `latest_model_score: 0.91`), and 8 supporting observations.
- `./scripts/validate_demo_environment.sh` (quick acceptance mode) **PASSED**
  against this live stack, including the new `ai_fault_*` checks
  (`ai_fault_active=yes`, `ai_fault_missing_fields=none`).
- Prometheus loaded all 8 new alert rules (`curl .../api/v1/rules` confirmed both
  rule groups); `fault_inference_results_total{status="valid_prediction"}` and
  `outbox_pending_events` were live, non-placeholder series.

This is the strongest evidence in this scorecard: the fixes above were not just
code-reviewed, they were watched working on a real Kafka/Postgres/Redis stack.

## 3. Health and readiness audit

| Service | Liveness | Readiness | Gap |
|---|---|---|---|
| api | `GET /live` | `GET /ready` (postgres, redis, kafka, worker heartbeat) | none — this is the reference pattern |
| worker | `pgrep` | `/ready` reflects worker heartbeat via the API | none |
| fault-inference-worker | `pgrep` | Verifies the promoted model artifact (SHA-256 + schema) and connects Kafka consumer/producer **before** the process is considered started — but the Compose healthcheck itself is still liveness-only (`pgrep`), not a dedicated readiness probe | No dedicated `/ready`; process-alive and artifact-verified are conflated in practice (a `pgrep`-passing process that failed artifact verification would have already exited, so this is lower-risk than it sounds, but it's not a clean readiness signal) |
| reasoning-bridge-worker | `pgrep` | Connects Kafka consumer/producer before processing | Same gap as above |
| postgres / redis / kafka / mosquitto | image-native healthchecks | — | none |
| frontend | `GET /` | — | none |
| prometheus / grafana | `/-/healthy` / `/api/health` | — | none |

**Startup failure behavior verified by design (not re-tested live this pass):**
missing/corrupt model artifact → worker exits non-zero before reporting healthy
(`backend/simulator/inference/loader.py` hash/schema verification, confirmed present
in the infra audit); Kafka unavailable at startup → both workers fail fast with a
named structured log event and `sys.exit(1)`, not silent retry.

## 4. Failure-mode matrix

| Failure | Expected behavior | Status |
|---|---|---|
| Inference worker restart | Warm-up resets to zero (in-memory state only) | As designed, documented in `runtime-inference.md` |
| Reasoning worker restart | Durable evidence/idempotency preserved (Postgres + deterministic UUIDv5 event IDs) | Verified by existing tests (`test_duplicate_replay_does_not_create_a_second_investigation`) |
| Kafka replay | Deterministic IDs prevent duplicate domain effects | Verified by existing tests; SSE invalidation may fire again on replay — explicitly acceptable (it's a refetch signal, not a state mutation) |
| Outbox dispatch failure (Kafka leg) | Durable outbox retained for retry | **Fixed this pass** — was previously silently dropped; now has a regression test |
| HTTP persistence branch fails (in `kafka+http`) | Kafka may succeed independently; not one atomic transaction | As designed and documented (`kafka-fault-inference-worker.md`'s "Single-source telemetry provenance"); deterministic `observation_id()` means an HTTP retry after a Kafka-only success is rejected 409, not double-persisted |
| Incomplete telemetry | Data-quality event, no false healthy | As designed (`odis.fault.telemetry-data-quality.v1` topic) |
| Feature rejection | `insufficient_data` status, alert semantics preserved | As designed (`numerically-safe-features.md`'s explicit rejection path, not null-imputation) |
| Browser SSE disconnect | Last durable state remains visible | **Fixed this pass** for the two components that violated this (stale-data-on-error bug) |
| Unsupported event version | Rejected and observable | As designed — `SUPPORTED_INPUT_EVENT_VERSIONS` check, logged + metriced, not silently dropped |

## 5. Event-contract inventory

| Event | Producer | Consumer(s) | Version field | Deterministic identity | Malformed-event behavior |
|---|---|---|---|---|---|
| Telemetry observation | Simulator (`kafka+http`/`kafka` transport) | Fault-inference worker | `event_version="v1"` | Deterministic per (asset, timestamp, measurement) | Rejected with a logged reason, counted in `fault_inference_malformed_events_total{reason}`, not dropped silently |
| `fault_inference.v1` | Fault-inference worker | (informational / metrics; not directly consumed downstream) | in topic name | Deterministic UUIDv5 keyed on source sample | — |
| `fault_alert_transition.v1` | Fault-inference worker | Reasoning bridge worker | in topic name | Deterministic UUIDv5 | Malformed events logged + metriced (`reasoning_bridge_malformed_events_total{reason}`) and dropped — no DLQ topic for this one specifically (asymmetric vs. the inference worker's own data-quality topic; documented as intentional, not a bug) |
| `fault_reasoning_result` (`odis.fault.reasoning-results.v1`) | Reasoning bridge worker | (informational / metrics) | in topic name | Deterministic UUIDv5 | — |
| `fault_investigation_updated` (SSE signal) | API, via outbox → Redis | Dashboard (React Query cache invalidation) | — | Not required — invalidation is idempotent by construction (it triggers a refetch, not a state mutation) | A duplicate/replayed invalidation is explicitly acceptable |

**Backward-compatibility policy:** all four Kafka topics carry an explicit version
field; consumers reject unsupported versions rather than guessing. No schema
registry — versioning is a convention, documented per-topic in
[Kafka Fault Inference Worker](../kafka-fault-inference-worker.md) and
[Reasoning Bridge](../reasoning-bridge.md).

## 6. Outbox recovery verification

- Domain state and outbox row are committed atomically (same Unit-of-Work transaction) — unchanged, already correct.
- **Fixed this pass**: a failed Kafka-leg dispatch now leaves the row undispatched (previously always marked dispatched).
- Retry succeeds on a later `dispatch()` cycle — verified by
  `test_retry_dispatch_succeeds_after_transient_kafka_failure`.
- Replay does not create duplicate monitoring effects beyond acceptable SSE
  invalidations — unchanged, already correct, covered by existing idempotency tests.
- Outbox growth is **not yet bounded** (no cleanup/archival job) — deferred to a
  follow-up; flagged here as an operationally-visible known gap rather than a silent
  one, and now has a Prometheus gauge (`outbox_pending_events`) plus an alert rule
  (`ODISOutboxBacklogGrowing`) so it's observable in the meantime.

## Remaining limitations

- **No from-scratch `pytest -m integration` full-chain test was added.** The live
  validation in §2 exercised the real chain end to end and is strong evidence the
  wiring works, but it was a manual, one-time run in this session — not a repeatable,
  CI-triggerable assertion. `scripts/validate_demo_environment.sh --walkthrough` is
  the closest thing to a repeatable version of this and was hardened in this pass,
  but it isn't wired into CI (the task explicitly allows this: "may remain manual...
  but the repository should have one explicit command to run it" — that command is
  `./scripts/validate_demo_environment.sh --walkthrough` against a running Compose
  stack).
- Readiness probes for the two new workers remain liveness-only (`pgrep`); a
  dedicated `/ready` was not added this pass.
- Outbox row cleanup/archival was not implemented, only made observable.
- k8s manifests for the two new workers do not exist yet — the k8s Prometheus
  scrape config was left un-configured for them (with an explanatory comment)
  rather than pointing at services that don't exist.
- This scorecard reflects a single hardening pass scoped to Blocker/High findings
  by explicit user decision; several Medium/Low findings from the underlying audit
  remain open (see [Files changed](#1-findings-and-fixes) deferred list above).

## Final verdict

**ODIS v1.1 DEMO READY WITH DOCUMENTED LIMITATIONS.**

The AI-fault-alert pipeline was verified working end to end on live infrastructure
during this hardening pass, after fixing a Blocker-level gap that meant it was
previously unreachable from the standard demo command at all. The remaining gaps
(readiness probes, outbox cleanup, a CI-wired full-chain test) are real, documented,
and scoped as explicit follow-ups rather than hidden — none of them block a
portfolio demo of the capability this release actually built.
